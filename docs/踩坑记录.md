## 1. 中文输入法 + xterm.js

中文 IME 在终端中输入是已知的难点。后续实现要点:
- xterm.js 的 `onData` 事件拿到的不是 IME 合成后的最终文本
- 需要监听 `keydown` 而非 `onData` 处理输入法
- 设置 `applicationCursor`、`applicationKeypad` 模式按需
- 持续在 Linux / macOS / Windows + 搜狗/微软/QQ 输入法下测试

## 2. ZMODEM 协议

v0.17.0 使用 `zmodem.js` 在 Webview 侧实现 `rz` / `sz` 协议:
- SSH 输出事件必须传 `Vec<u8>` JSON 字节数组,禁止先 `String::from_utf8_lossy`;ZMODEM 是二进制协议,一次 UTF-8 损失转换就会破坏握手和文件
- 前端所有 SSH 输出先经过 `Zmodem.Sentry`;普通终端字节由 `to_terminal` 交给 `TextDecoder(stream:true)` 与 xterm,ZMODEM 字节由 session 消费
- 协议回包通过 `ssh_write_binary(Vec<u8>)` 写入 russh channel;普通键盘输入仍走 `ssh_write(String)`
- 远端执行 `rz` 时弹出本地文件选择条并发送;远端执行 `sz <file>` 时接收后触发本地保存
- 后续若替换协议库,必须保留“端到端原始字节”边界并用真实 lrzsz 主机做双向回归

## 4. Sidecar 通信

- MVP 用 `stdio JSON-RPC`(Go `bufio.Scanner` 读 stdin)
- Rust 侧读写循环分离,按请求 ID 关联并发响应,单次 RPC 默认超时 120 秒
- 启动时必须完成协议版本与关键 RPC 能力握手,禁止加载旧 Sidecar
- 性能敏感场景升级到 `gRPC over Unix Socket`
- 协议版本号:Sidecar 启动时打印,便于排查

### 4.1 Sidecar 路径解析

`SidecarManager::start()` 通过 `std::env::current_exe()` 获取主程序 exe 路径,然后按优先级检查以下候选路径:

| 优先级 | 路径 | 场景 |
|---|---|---|
| 1 | `<exe_dir>/starhub-sidecar[.exe]` | 生产环境:sidecar 与主程序同目录 |
| 2 | `<exe_dir>/sidecar/starhub-sidecar[.exe]` | 生产环境:sidecar 子目录 |
| 3 | `<exe_dir>/../sidecar/bin/starhub-sidecar[.exe]` | 开发环境:主程序在 `src-tauri/target/<profile>/` |
| 4 | `<exe_dir>/../../sidecar/bin/starhub-sidecar[.exe]` | 开发环境备用 |
| 5 | `<exe_dir>/../../../sidecar/bin/starhub-sidecar[.exe]` | 开发环境:主程序在 `src-tauri/target/debug/` |

**开发时**:Windows 主程序位于 `src-tauri/target/debug/starhub.exe`,Unix 主程序为 `src-tauri/target/debug/starhub`;Sidecar 分别为 `sidecar/bin/starhub-sidecar.exe` 与 `sidecar/bin/starhub-sidecar`。

**打包时**:需确保 sidecar 二进制与主程序 exe 放在同一目录(或 `sidecar/` 子目录)。推荐配置 `tauri.conf.json`:

```json
{
  "bundle": {
    "externalBin": ["../sidecar/bin/starhub-sidecar"]
  }
}
```

> ⚠️ Go sidecar 编译时必须指定正确的 `GOOS` 和 `GOARCH`(如 `GOOS=windows GOARCH=amd64`),否则二进制无法在目标平台运行。

## 5. Tauri 2 跨平台打包

- macOS arm64 + x86_64 需双架构打包(用 `cargo tauri build --target universal-apple-darwin`)
- Windows 代码签名需 EV 证书(否则 SmartScreen 警告)
- Linux 固定 Ubuntu 24.04 / glibc 2.39 基线,使用原生 x86_64 与 ARM64 runner 分别构建,禁止跨架构生成 AppImage
- **截图栈(xcap → pipewire/libspa 0.10.1)要求系统 PipeWire/ spa 头 ≥ 1.0**:`libspa-sys` 的绑定是构建时用 bindgen 从系统 spa 头生成的,Ubuntu 22.04 的 0.3.48 头缺 `spa_video_info_raw.flags` 且 `spa_meta_region_is_valid`/`spa_meta_first` 还是宏(bindgen 无法导出成可调用函数),`libspa 0.10.1` 编译报 E0425/E0560/E0308 一串错误——这就是「Windows 用 WGC 后端不碰该链所以绿、GitHub Linux 必挂」的原因;Linux 构建基线因此定在 24.04,旧系统运行时由 `screenshot_begin_region` 预检 `pipewire --version` 提示升级到 Ubuntu 24.04+
- **截图栈 Linux 编译依赖(xcap 官方清单)**:`libpipewire-0.3-dev libspa-0.2-dev libgbm-dev libegl-dev libwayland-dev libxcb1-dev libxrandr-dev libdbus-1-dev`——`libgbm-dev` 缺失时链接期报 `rust-lld: unable to find library -lgbm`(Wayland 后端 libwayshot-xcap → Rust `gbm 0.18` FFI 直链)
- Linux 每个架构必须同时产出 AppImage、DEB、RPM;AppImage 内置 WebKitGTK/GTK 与静态 Go sidecar,DEB/RPM 由包管理器解析系统依赖
- `scripts/verify-linux-bundles.sh` 必须校验三类包、架构、sidecar 执行权限/静态链接、DEB/RPM 依赖和 `ldd` 的 `not found`;缺一项不得发布
- AppImage 面向主流 glibc 桌面发行版,不宣称兼容 Alpine(musl)或无 FHS 兼容层的 NixOS;无 FUSE 环境使用 `--appimage-extract-and-run`

## 6. 应用图标管理(重要)

> 换 Logo 时最容易踩的坑:改了打包图标但应用内 / 快捷方式还是旧的。

**图标存在 3 个独立位置,必须全部更新才不漏**:

| 位置 | 文件 | 作用 | 更新方式 |
|---|---|---|---|
| 打包图标 | `src-tauri/icons/icon.ico` / `icon.png` / `icon.icns` / 各尺寸 PNG | exe 图标、桌面快捷方式、任务栏、托盘 | `npx @tauri-apps/cli icon <源图.png>` 一键生成全套 |
| 应用内标题栏 | `src/assets/logo-star.png` + `CyberLayout.vue` 的 `.logo` | 自定义标题栏左上角 Logo(`decorations: false` 时系统标题栏不渲染,Logo 全靠前端画) | 替换图片 + 确认模板用 `<img :src>` 而非 CSS 几何图形 |
| 前端其他引用 | `src/assets/logo.png` 等 | 设置页、关于弹窗、Loading 等场景 | 全局搜索 `logo` 确认无遗漏 |

**换 Logo 标准流程**:

1. 准备一张 1024×1024 透明背景 PNG,放入 `icons/_candidates/`
2. 用 `npx @tauri-apps/cli icon icons/_candidates/xxx.png` 生成 `src-tauri/icons/` 全套(ICO/ICNS/PNG/iOS/Android/Store Logo)
3. 把生成的 `icon.png` 复制到 `src/assets/logo-star.png`(标题栏用)
4. 确认 `CyberLayout.vue` 模板中 `.logo` 用 `<img :src="logoUrl">`,不是 CSS 画的几何图形
5. 全局搜索 `logo.png` / `icon.svg` / `logo-mark` / `logo-core` 确认无残留旧引用
6. **清 Tauri 构建缓存**:`cargo clean -p starhub`(否则 exe 里嵌的还是旧图标)
7. 重新 `npm run tauri build`

**踩过的坑(v0.13.2 ~ v0.13.5)**:

- ❌ 源图是 JPEG 伪装成 .png → `tauri icon` 生成的图标无透明通道,exe 显示为带米黄背景的方形
  - 修复:用 .NET `System.Drawing` 转真 PNG + `LockBits` 把背景色设为 Alpha=0
- ❌ 标题栏 Logo 用 CSS 画的 `S` 轨道几何图形(`.logo-mark` / `.logo-orbit` / `.logo-core`),换 Logo 后应用内不变
  - 修复:CyberLayout 模板改为 `<img :src="logoUrl">`,删除 CSS 几何 Logo 样式
- ❌ 改了 `icon.ico` 但 exe / 快捷方式还是旧图标 → Tauri 构建缓存(`target/`)里嵌的旧图标
  - 修复:`cargo clean -p starhub` 后重新打包
- ❌ `icon.svg` / `icon-source.svg` 仍是旧设计 → `tauri icon` 不生成 SVG,需要手动用 `icon.png` base64 嵌入 SVG `<image>`
- ❌ Windows 安装后桌面快捷方式图标不更新 → Windows 图标缓存问题
  - 修复:`ie4uinit.exe -show` 或重启资源管理器

## 7. Univer 视图下方留白与 CSS 类名冲突

> **⚠️ 已废弃** (2026-08-26): StarHub 的 Excel 前端已不再使用 Univer 渲染(改用 CodeMirror + 后端 Go excelize 直写 xlsx),`vendor/univer` / `vendor/univer-presets` 两个 submodule 已移除。以下内容仅作历史踩坑记录保留,不再适用于当前代码。
>
> v0.14.6 ~ v0.14.14 曾连续从尾行数量、canvas resize、grid 模板和 flex 高度链排查 Excel 下方留白,最终在 v0.14.15 通过 Vite 真实 DOM 尺寸测量找到根因。后续 Agent 遇到类似问题必须先量尺寸,不要继续凭视觉猜高度。

**最终根因**:

- StarHub 原本把 Univer 挂载容器命名为 `.univer-grid`
- Univer 0.25.1 自己也提供全局 Tailwind 工具类 `.univer-grid { display: grid }`
- 全局样式污染挂载容器后,504px 高度被浏览器自动拆成约 `290px + 214px` 两个 grid 行
- `[data-u-comp="workbench-layout"]` 只占第一行,第二行就是截图中的整块留白;因此继续给 Workbench 内部补 `height:100%` / `flex:1` 无法解决外层分行

**修复与硬约束**:

1. Univer 挂载根必须包含 `.univer-host`(数据库结果可同时带 `.db-univer-host`),禁止改回 `.univer-grid`
2. 新增第三方组件挂载类时,必须先检查其编译 CSS 中是否存在同名全局工具类
3. 留白问题先在 Vite dev server 注入可重复 mock 数据,同时测试默认窗口与用户截图尺寸
4. 用 `getBoundingClientRect()` + `getComputedStyle()` 从外向内记录:
   - StarHub shell
   - 挂载根
   - `[data-u-comp="workbench-layout"]`
   - `[data-range-selector]`
   - 数据 canvas
5. 正确状态是挂载根与 Workbench 等高、`data-range-selector` 与数据 canvas 等高;若父层已被拆行,不要先改 canvas resize
6. 修复后必须在浏览器截图确认网格连续铺到 Sheet 标签栏,并检查控制台无新增错误
7. 覆盖 Univer 内部布局时必须限制到直接子级(例如 `> section > .univer-grid`),禁止用后代选择器覆盖全部 `.univer-grid`;后者会误伤 Ribbon 内部网格并把工具按钮折叠成省略号
8. Sheet 切换禁止 dispose/recreate Univer。工作簿首次加载后只调用 `workbook.setActiveSheet()`,仅在缓存对象真正替换时用 `setValues()` 原地同步数据
9. 数据库分页、排序、刷新和保存后也必须保留 `DbUniverGrid` 实例,用 loading 遮罩 + 原地 `setValues()` 更新,否则会闪白并丢失滚动位置

**本次实测判据(v0.14.15)**:

- 修复前:`.univer-grid` 挂载根 `display:grid`,`grid-template-rows: 290px 214px`,Workbench 高 290px
- 修复后:`.univer-host` 挂载根 `display:block`,挂载根与 Workbench 均高 504px,数据 canvas 与 `[data-range-selector]` 均高 399px

## 8. SFTP Subsystem 路径错误与受控降级

- `russh` 的 `request_subsystem(true, "sftp")` / `exec(true, ...)` 只负责发送 channel request；必须继续读取 channel 的 `Success` / `Failure`，否则服务端拒绝会被后续 `russh-sftp` 初始化误判成 Timeout。
- 建链期间必须区分 stdout 的 SFTP 二进制协议与 `ExtendedData` stderr，并完整保留 exit status、exit signal、request failure 和提前关闭状态。面向用户的错误不得只显示 `[SFTP_FAILED]` 或 Timeout。
- 默认 `sftpLaunchMode=auto`：先使用标准 subsystem，确认是可恢复的服务端启动失败后才执行固定探测脚本；找到可执行 `sftp-server` 才用 SSH exec 降级。真实网络超时、SSH 通道打开失败等错误不自动重试为 exec。
- `subsystem` 模式用于严格禁止降级；`custom` 模式只接受远端 Unix 绝对路径，后端必须再次做长度、控制字符校验和 POSIX 安全引用，禁止接收任意命令文本。
- 自动探测失败时要同时展示 subsystem 原始错误与探测结果，并建议服务端优先改为 `Subsystem sftp internal-sftp`、执行 `sshd -t` 校验后 reload sshd。

## 9. AI 多轮上下文与会话绑定

- Planner 必须接收有界的历史对话,不能只发送当前输入;重试和结构化选项重新规划时要移除一次重复的当前请求。
- 顺序 Executor 必须注入已经完成的前置步骤结果;同一并行批次不得读取仍在执行的兄弟步骤结果。
- `runAgent` 必须在追加流式 assistant UI 占位前复制消息快照,禁止把空 assistant 发送给 Provider。
- 正式 tab 会话只持久化有界的用户/助手文本,不得把工具参数、工具原始输出、执行计划或 `#` 工具绑定写入 localStorage;恢复后工具范围为空。
- `#` 上下文在当前对话内沿用并持续可见,模块引用必须在绑定时固化为具体资产 ID,不得因后来新增资产扩大范围;清除按钮、新对话和应用重启都撤销绑定,写操作与高危动作继续逐次确认。
- AI 消息滚动位置由 keep-alive 页面实例在停用时捕获、激活后恢复;原本停留在底部的会话继续跟随新增内容,用户正在回看历史时不得强制跳到底部。
- 全局 AI 的 SSH 工具只能使用 exec-only 连接,禁止申请 PTY 或启动远端 shell;手动 SSH 标签页继续使用交互式 PTY,两条路径不得混用。

## 10. Windows 上 `dragDropEnabled` 与 HTML5 DnD 冲突(重要)

- `tauri.conf.json` 的 `dragDropEnabled: true` 是 SFTP / Excel 拖 OS 文件进窗口(`getCurrentWebview().onDragDropEvent`,拿完整路径)的前提,不能关。
- 但 Tauri 官方文档明确:**Windows 上开启它会拦截 HTML5 drag-and-drop**,`draggable` + `dragstart` / `dragover` 全部失效(macOS / Linux 不受影响)。
- 因此窗口内的"拖动手势"(如标签页拖出独立窗口)必须用 **Pointer Events + `setPointerCapture`** 自实现,禁止回到 HTML5 DnD;capture 还能保证拖出窗口外持续收到 move/up。
- 注意 pointer capture 会把拖拽后的 `click` 派发到源元素,需要一次性屏蔽(`suppressNextTabClick`)。**禁止用定时器屏蔽**(click 派发被事件循环延迟时定时器会先失效);要用 window capture 阶段的一次性 click 吞听器,并以 `pointerdown` once 监听兜底撤掉,避免误吞正常点击。

## 11. 标签页拖出独立窗口白屏(v0.32.6)

- 版本:v0.32.5 及之前
- 现象:把标签页拖出为独立窗口后,新窗口只有纯色背景,看不到标题栏和工作区内容(用户描述为"白屏")
- 根因(双重):
  1. `src/lib/windowDetach.ts` 的 `buildDetachedUrl` 生成 `index.html?detach=1&route=...`。Tauri WebviewWindow 加载后,`createWebHistory()` 拿到的初始 path 是 `/index.html`,而路由表只有 `/` 及其子路由,`/index.html` 不匹配任何路由,根 `<router-view/>` 渲染为空,CyberLayout 根本不会挂载。
  2. 即便把 URL 改成 `/`,`src/components/layout/CyberLayout.vue` 在独立窗口分支里调用 `assetStore.fetchAssets()` 时没有 `await`;`router.replace(detachedInfo.route)` 会抢在资产列表返回之前挂载 SshTerminal / DbView / DockerView 等组件。这些组件在 `onMounted` 里发现 `asset` 为空,会执行"资产已被删除 → 关闭 tab 并 `router.push('/')`"的兜底逻辑,把工作区推回空白占位页。
- 修复方案:
  1. `buildDetachedUrl` 返回 `/?${params.toString()}`,让新窗口初始 path 就是 `/`,与主窗口一致,CyberLayout 能正常挂载。
  2. 独立窗口 `onMounted` 里 `await assetStore.fetchAssets()` 完成后再 `router.replace(detachedInfo.route)`,确保工作区组件挂载时资产已就绪。
- 后续硬约束:
  1. 任何通过 `new WebviewWindow` 打开同应用页面的 URL 都必须用 `/` 或 `/path` 形式,禁止再传 `index.html` 给 vue-router 的 `createWebHistory`。
  2. 独立窗口的精简初始化若依赖 store 数据,必须等待数据就绪再让 `<router-view/>` 渲染依赖该数据的组件;否则要在组件内部识别 detached 模式并跳过"缺失即关闭"兜底。
  3. 新增类似"用 query 参数做窗口间协议"的功能时,先用浏览器打开 `/?key=value` 验证路由能匹配到目标组件,再进 Tauri 真窗口验证。

## 12. `v-show` 对多根节点组件静默失效(v0.39.1)

- 版本:v0.39.0(提交 75aee46 引入)
- 现象:DbDashboard 指标卡按 概览/性能/网络 tab 分组,点击「性能」「网络」tab 高亮变了但卡片网格毫无变化,用户感知为"没有内容"。
- 根因:`DashboardCard.vue` 是双根节点组件(`<button>` + `<v-dialog>` 并列,渲染为 Fragment)。Vue 3 的 `v-show` 作用于 Fragment 根组件时完全不生效,dev 下只打一条 `[Vue warn]: Runtime directive used on component with non-element root node`,display 永远不切换。
- 修复:把 `v-show` 从卡片组件上移到普通 `<div class="dashboard-grid">` 容器,每个 dbType 块内按 tab 拆 2~3 个容器;不能用 `v-if` 替代(切 tab 会销毁卡片,丢失 `sampledHistory` 趋势采样)。
- 后续硬约束:
  1. 给组件加 `v-show` 前先确认它是单根;多根组件(尤其是含 teleport/v-dialog 并列根的)一律把显隐控制放到外层原生元素上。
  2. dev console 出现 "Runtime directive used on component with non-element root node" 警告必须当 bug 处理,不能跳过。

## 14. rustls 双 CryptoProvider 导致 `ClientConfig::builder()` panic(v0.46.9)

- 现象: 「服务器网页访问」打开 HTTPS 站点(如 www.baidu.com)时,iframe 报 Chromium 错误页「127.0.0.1 未发送任何数据」(ERR_EMPTY_RESPONSE);HTTP(80 端口)站点正常。

  1. 只要依赖树里 rustls 0.23 同时带 `ring` 与 `aws-lc-rs`(Cargo.lock 的 rustls 条目 dependencies 里两个都出现),任何 `ClientConfig::builder()` / `ServerConfig::builder()` 调用点都必须改为 `builder_with_provider` 显式指定。

## 15. SSH AI 多行命令「prompt 返回超时」与 keep-alive 滚动锚点被离屏 DOM 清零(v0.47.2)

- 现象 A:AI 在 SSH 终端执行多行命令(如 `for n in ...; do tail -3 ...; done`),命令秒回,却等满 60s 报「等待 shell prompt 返回超时,已发送 Ctrl+C 恢复终端」。

- 现象 B:AI 助手(AiView)/ SSH 内嵌 StarAI 面板切换标签页后回到对话开头。
- 根因 B:Vue keep-alive 失活时**先把 DOM 移入离屏容器,再触发 deactivated 钩子**(runtime-core `deactivate`:先 `move` 后 `invokeArrayFns(instance.da)`);离屏元素 scrollTop 读数为 0,`onDeactivated` 里的 capture 用 0 覆盖了 `@scroll` 记录的正确锚点,激活后恢复到顶部。
- 修复 B:`onDeactivated` 里先判 `container.isConnected`,已离屏就保留 `@scroll` 记录的最后锚点;AiChat 补齐同样的锚点保存/恢复;恢复改为「同步一次 + rAF 校正一次」双保险(后台窗口 rAF 可能不触发)。
- 后续硬约束:

## 16. 网页访问 iframe 报「127.0.0.1 拒绝连接」实为 X-Frame-Options / CSP frame-ancestors 拦截(v0.47.4)

- 现象: 「服务器网页访问」打开 www.baidu.com,iframe 只显示一个红色禁止图标(Chromium 子帧错误页),主帧打开的错误文案是「127.0.0.1 拒绝连接 / refused to connect」。同一时刻 `curl` 直连网关端口却完全正常(200 + 改写后 HTML,SSH 隧道链路通畅)。
- 根因: 这**不是** TCP 层的 `ERR_CONNECTION_REFUSED`,而是 `ERR_BLOCKED_BY_RESPONSE`——网关把上游站点的 `Content-Security-Policy: frame-ancestors 'self' ...`(以及部分站点的 `X-Frame-Options`)原样透传给 webview,`frame-ancestors` 白名单里没有 `127.0.0.1`,Chromium 拒绝把响应渲染进 iframe。其错误页文案恰好是「<host> 拒绝连接」,与端口失效的表现一模一样,导致此前数版修复都在排查监听端口存活 / accept 循环,方向全错。
- 排查手段(可复用):
  1. `netstat -ano | findstr LISTENING` 按 starhub.exe 的 PID 确认网关端口确实在监听;
  2. `curl -D - "http://127.0.0.1:<port>/__proxy__/https/<host>/"` 绕过 webview 直验网关全链路(curl 不执行 XFO/CSP,能通就说明 TCP/SSH/TLS 都没问题);
  3. 审计库 `%APPDATA%/com.starhub.app/starhub.db` 的 `audit_log` 表 `web_access` 记录里有 `gatewayPort`,可核对前端实际使用的端口(注意 WAL 未 checkpoint,要连 `-wal` 一起拷)。
- 修复方案: `src-tauri/src/ssh/web_gateway.rs` 回写响应时统一经 `should_skip_response_header` 过滤,剥离 `x-frame-options` / `content-security-policy` / `content-security-policy-report-only`(整个 CSP 一并剥离:改写后的页面经 127.0.0.1 源加载,上游 CSP 的 script-src / img-src 等指令同样会拦截改写产物);新增单测与端到端断言(百度实测会发 frame-ancestors);网关启动、上游失败、上游超时补 `tracing` 日志。
- 后续硬约束:
  1. 再遇「127.0.0.1 拒绝连接」先分清 `ERR_CONNECTION_REFUSED`(端口没人听)与 `ERR_BLOCKED_BY_RESPONSE`(XFO/CSP 拦截嵌入):curl 能通而 iframe 不通,必是后者,直接去查响应头。
  2. 网关/代理类转发上游响应头时,嵌入拦截类头(XFO、CSP、CSP-Report-Only)默认剥离;调整透传头清单时同步更新 `should_skip_response_header` 的单测。

## 26. .bat 文件里的 UTF-8 中文注释会炸 cmd 解析(v0.79.0)

- **工具卡文件链接的悬空陷阱**:卡片上的文件名可点击,点击走 `local_read_text_file`(src-tauri/commands/local.rs L345 起)读实时元数据与正文;若目标文件已被删除(AI 当场建的临时验证文件清理后就中招),错误以裸 OS 文案直达 UI:`read metadata failed: 系统找不到指定的文件。 (os error 2)`。后续版本应把该错误降级为友好提示(如「文件已不存在」),并在 diff 卡层面对悬空路径给出状态标记。

## 29. Rust ↔ sidecar 参数键名漂移:docker_exec 静默坏了一个版本段(v0.105.0)

- **症状**:`docker_exec` 域工具自「方案1:域工具迁 Rust 进程内执行」后实际一直失败,但无用户报告——直到沙箱桌面 M1 复用 `docker.exec` 时逐字段核对 sidecar handler 契约才发现。
- **根因**:`harness/domain.rs` 的 `execute_docker` 发 `{"container", "cmd"}`,而 sidecar `adapters/docker.go` 的 handler 结构体是 `containerId`/`command`(json tag)。两侧各自能编译、各自有测试,但**键名契约没有任何一处共享定义**,漂移零告警。
- **修复**:对齐为 `containerId`/`command`;沙箱桌面模块建立新约定——**新增 sidecar 调用前先读 handler 的 struct json tag,不复读调用方既有代码**。
- **后续硬约束**:Rust 与 Go 之间的 RPC 参数契约以 sidecar handler struct 为唯一事实来源;给 sidecar 加新方法时,在 `handlers.go` 注册处顺手核对一遍既有调用方的键名。

## 30. sidecar RPC 120 秒默认超时截杀长耗时操作(v0.105.1)

- **症状**:AI 首次执行 `desktop_build_template` 报「Sidecar RPC timed out after 120 seconds」;镜像构建在 daemon 侧仍在继续,但工具调用已失败。
- **根因**:`SidecarManager::call` 固定 `DEFAULT_RPC_TIMEOUT = 120s`;镜像构建(5-15 分钟)、大层 commit、长 timeoutSec 的 docker exec 全部超过它。设计文档写了构建时长,落地时没核对这条链路的超时上限。
- **修复**:`call_with_timeout` 提为 pub,desktop 模块新增 `platform_call_with_timeout`——buildImage 1800s / commitContainer 600s / docker exec 跟随 timeoutSec+30s;超时不再硬失败,降级为落盘 Dockerfile + 返回手工 `docker build`/`docker commit` 命令指引(用户执行后重调即命中 daemon 层缓存)。
- **后续硬约束**:凡新增「可能超过 2 分钟」的 sidecar RPC,必须显式传超时,并在设计文档里写清该操作的最坏耗时;超时文案一律带人工降级路径(可手工执行的命令),不只报错。
- **旁证**:dsh 侧链路无隐藏超时——timeout-policy 只在工具声明 timeoutMs 时生效(bridged 工具未声明即无限),sdk-protocol transport.request 无默认超时,前端转发路径的 TOOL_EXEC_TIMEOUT=180s 只管 dsh://tool-exec(desktop_* 进程内执行不经此路)。

## 31. profiles/node_modules junction 钉死旧路径:升级后加载陈旧/开发树插件代码(v0.106.0)

- **症状**:用户安装了 v0.106.0 包(exe ProductVersion 与打包 runtime 均为新版),但 GUI 仍是旧版界面;`GET /plugins/@deepseek-ai/dsh-starhub-client-nav/client.js` 返回旧 bundle。
- **根因**:`web.rs` 物化 `$DSH_HOME/profiles/node_modules` 的本地包 junction 时是「`link.exists()` 则复用」——junction 目标在创建时钉死当时解析的 runtime 路径,之后永不校验。dev 与 release 共用同一 `%APPDATA%\com.starhub.app`(Tauri identifier 相同),dev 期建的 junction 指向 `vendor/deepseek-harness/packages/starhub/<pkg>`(源树,lib/ 被 gitignore 常过期),release 升级后继续经它加载旧 lib;同理安装目录变更(E:\StarHub1 → 别处)也会让 junction 指向化石路径。
- **修复**:`web.rs` 新增 `ensure_dir_link_fresh`:已存在的链接用 `symlink_metadata` + `read_link` + 双侧 `canonicalize` 校验指向,漂移/悬挂即删旧重建(junction 用 rmdir、Unix symlink 用 unlink);位置被真实目录占用时告警跳过,绝不删用户数据。LOCAL_PACKAGES 与 RUNTIME_HOSTED_PATCH_DEPS 两处循环统一走它,附 5 分支回归测试。
- **后续硬约束**:
  1. 任何「指向随版本/安装位置漂移的目标」的链接/缓存,建立时必须先校验既有指向,「存在即复用」只适用于目标恒定的场景;
  2. 判断链接是否存在用 `symlink_metadata`,不要用 `Path::exists()`——后者跟随链接,悬挂 junction 返回 false,mklink 又因「已存在」失败,永远卡死;
  3. Windows 上给 `mklink /J` 传参(经 Rust `Command`)必须用原生分隔符的分段 `Path::join`,整串含 `/` 的路径会让 cmd 内建解析失败(exit 1,无 stderr)。

## 32. 审批 never 策略短路 hard 确认:全访问下 desktop_exec 必拒(v0.106.0)

- **症状**:权限预设为 danger-full-access(全访问)时,`desktop_exec` 等恒确认(hard 档)工具调用直接报「the user rejected tool」,确认卡根本不弹;系统提示里出现 "Approval prompts are disabled in this session"。
- **根因**:两层策略互相矛盾。StarHub 风险门(approval-bridge)的设计意图是「hard 档删除/高危确认与预设脱钩,never 下也弹卡」,门也确实对 hard 返回了 `ask`;但 `dsh-user-approval` 服务的 `decide()` 在会话策略为 never 时**先于所有 answerer 直接 return "rejected"**,确认卡应答器永远收不到请求。approval-bridge 在 session/created 把 danger-full-access 映射为 never,正好踩进这个短路。
- **修复**(v0.106.1,两处协同,均不动 dsh 内核):① approval-bridge 任何 preset 都钉 `ask`,「全访问放行软确认」改由风险门按 preset 判定(折叠会话 `permission/preset` 事件,缺省读 settings.yaml 的 defaultPreset)——全访问 = 只有 hard 档(DELETE FROM/rm -rf/desktop_exec 等)弹确认,其余静默;② `examples/starhub-web/cordis.patch.yml` 覆盖 permission-presets 的 presets 表,danger-full-access 的 approval 由 never 改 ask(否则 /permission 切换又经 permission-presets 把 never 写回)。已在 never 卡住的老会话:重新切一次 preset(或新开会话)即恢复。
- **后续硬约束**:
  1. 给 dsh 审批体系接新档位时,确认卡的可达性要以「answerer 真的收到 approval/request」为验收点,不能只看风险门返回了 ask;
  2. StarHub 组合里禁止再把任何 preset 映射为 approval never;约束注记在 starhub-web patch 的 permission 行注释里(DSH_PERMISSION_MODE=danger-full-access 的 env 组合会派生 custom fail loud,勿设置)。

## 34. 沙箱桌面跑 GUI Linux 应用(微信为例):apt 受限、运行时依赖、中文输入与点击命中(v0.106.x)

- **背景**:在沙箱桌面(Ubuntu 24.04 / Xvfb / xfce)里跑微信官方 Linux 版(WeChat 4.1.1),验证 AI 用 `desktop_*` 工具操作真实 GUI 应用(扫码登录、选会话、发消息)的可行性。结论:可行,但依赖与交互各有硬坑。
- **安装链路(apt 在沙箱内不可用)**:受限容器里 `setegid/seteuid` 被禁、`/var/cache/apt/archives/partial` 不可写,`apt-get`/`apt-get download` 全挂(报 `E: Sub-process http returned an error code (112)`,配置阶段 `libxkbcommon-x11-0` 也因依赖不满足卡住)。**改用 `curl` 直接下载 .deb + `dpkg -i`(必要时 `--force-depends`)可正常落地**,`ldconfig` 后生效。给 apt 让缓存目录到 `/tmp`(`-o Dir::Cache::Archives=/tmp/x`)也解决不了 http 子进程降权问题。
- **运行时依赖(微信 deb 只声明 fonts-noto-cjk,实际缺一批,逐个 `ldd` 补齐)**:
  - `libatomic1`、`libxkbcommon-x11-0`、`libxcb-xkb1` / `libxcb-icccm4` / `libxcb-image0` / `libxcb-shape0` / `libxcb-render-util0` / `libxcb-keysyms1`(xcb 系列源在 `pool/main/x/xcb-util-*`,noble 版本带 `-buildN` 后缀)、`libnss3`+`libnspr4`、`libasound2t64`;
  - **libasound 版本陷阱**:`pool/main/a/alsa-lib/` 里 `tail -1` 会抓到更新发行版(plucky)的 `1.2.16.1`,它需要 GLIBC_2.43,而沙箱基线 glibc 2.39 → 运行时报 `version 'GLIBC_2.43' not found`。必须显式选 noble 的 `1.2.11-1build2`(或 `-1ubuntu0.x`),并用 `--force-downgrade --force-depends` 覆盖之前装错的版本;
  - `fonts-noto-cjk`:缺了中文渲染成乱码(登录页标题变成「送拉S崩吧」),装完 `fc-cache -f` 生效。
- **中文输入**:`xdotool type '中文'` 报 `Invalid multi-byte sequence`(`xdo_enter_text_window` 只认当前键位,不支持 CJK)。**用 `printf '...' | xclip -selection clipboard` + `xdotool key ctrl+v` 粘贴**即可(基础镜像无 xclip/xsel,需先装 xclip)。
- **GUI 自绘按钮点击不生效**:`desktop_click` 点「Send(S)」发送按钮多次不触发,改为**聚焦输入框后按回车**(`desktop_press_key Return`)发送成功。对这种自绘按钮,回车命中比像素级点击更可靠;按钮上的 `(S)` 即 Send 的快捷键提示。
- **坐标换算**:`desktop_screenshot` 落盘是 1920×1080,但 `read_image` 给模型的是缩小到 1066×600 的图——读图估点后要 **×1.8** 换算成物理像素再 `desktop_click`,否则点偏到桌面空白(表现为「点了没反应」)。
- **登录态**:微信 `~/.xwechat/login/wxid_*` 会话存档仍在,但**硬杀死主进程(`pkill -9`)后重启会退回登录页**,需重新扫码;正常退出才保留登录态。排查渲染时反复重启会打断登录态,慎用。

## 35. Android 实体机 adb 通道:exec-out CRLF、input text 转义、scrcpy 协议钉版本(v0.107.0)

- **背景**:Android 实体机直连(设计 `docs/superpowers/specs/2026-08-30-android-device-design.md`)落地时按 scrcpy/ADBKeyBoard 源码与实测确认的一组 adb 交互坑,全部固化进 `src-tauri/src/android/mod.rs` 纯函数与单测。
- **exec-out CRLF 二进制损坏(adb < 1.0.41,Windows)**:`adb exec-out screencap -p` 在旧版 Windows adb 上把每个 `\n` 改写为 `\r\n`(原有 `\r\n` 变 `\r\r\n`),PNG 流损坏。**修复方向是「k 个 \r + \n → k-1 个 \r + \n」,不是无脑删 \r**——PNG 8 字节 magic 自身就含合法 `\r\n\x1a\n`(初版修复把合法 CRLF 也删掉,单测抓住);magic 恰好是现成探针:先验 magic,不过再修复重验,仍不过报「升级 platform-tools」。初版只验前 4 字节 `\x89PNG` 也抓不到损坏(损坏流前 4 字节不变),必须验全 8 字节。
- **`input text` 双层转义**:`%` 是 input 命令的格式符(字面量 `%%`、空格 `%s`),先做这层转义,**再**套 shell 单引号(`sh_quote`,内部 `'`→`'\''`)防 toybox sh 展开;只支持 ASCII 可打印,非 ASCII(中文)走 ADBKeyBoard 广播(`am broadcast -a ADB_INPUT_TEXT --es msg`,需 `pm path com.android.adbkeyboard` 探测,未装给安装引导,不静默失败)。
- **unauthorized / offline 状态**:`adb devices` 状态非 `device` 时一切操作报「error: device unauthorized」——`android_connect` 探测状态并直接引导「请在手机上点『允许 USB 调试』」,`android_list_devices` 输出逐台标注。
- **scrcpy-server 协议与版本钉死**:server 首参必须等于自身版本号(`SCRCPY_SERVER_VERSION` 与 bundled jar 同步,不匹配即退出);`tunnel_forward=true` 时视频 socket 布局 = 1 哑字节 + 64B 设备名 + 12B codec meta + 帧(12B 元头:u64 BE pts+flags,bit63=config、bit62=keyframe,u32 BE size);版本升级必须按对应版本 `Options.java` 复核参数键名与协议(`resources/scrcpy/PROVENANCE.md` 记录了升级步骤)。下载二进制一律用官方 release 的 `SHA256SUMS.txt` 校验(v0.107.0 曾因 `Invoke-WebRequest .Content` 返回字节数组导致哈希比对脚本假死,改用 `curl.exe` 拉文本比对)。
- **control=false 的取舍**:无控制通道 ⇒ 无法请求关键帧,客户端从环形缓冲最近关键帧重同步,开播/丢帧后黑屏 ≤ 一个 GOP(12fps × 默认 GOP 约数秒);接管输入一律走 `adb shell input`(mpsc 入泵),不经 scrcpy。
- **adb forward 端口 TOCTOU**:`bind 127.0.0.1:0` 抢号后释放再 `adb forward`,窗口内有竞争;同一 serial 的 scrcpy 会话由注册表去重,旧窗口销毁时 best-effort `adb forward --remove`。
- **直播页坐标映射**:一律「显示矩形 → 设备物理像素」(`meta.width/height` = `wm size` 物理分辨率),与视频是否被 max_size 缩放无关;旋转后页面按新帧自然重排,历史坐标作废,需重新截图估点。

## 36. Android 截图坐标「点偏 1.3 倍」:模型看到的是缩略图,不是落盘原图(v0.108.0)

- **现象**:AI 连点多次都落在目标左上方(如搜索图标在物理 (995,215),连点 (715,147)/(745,148) 全空),自查对话才发现换算关系来回搞反。
- **根因**:`android_screenshot` 落盘是设备物理分辨率 PNG(如 1200x2670),但模型经 `read_image` 看到的是 harness 缩小后的图(920x2047)——缩小提示「multiply coordinates by 1.30」是给「读图」用的,而 `android_tap` 描述只写「物理像素」,两条提示词之间没有任何一座桥,模型只能自己悟。这不是坐标映射 bug(`input tap` 直吃物理像素,回放帧核对无误),是**工具契约文本缺一环**。
- **修复**(三处协同):① `capture_screenshot` 直读 PNG IHDR 返回当次真实宽高——**不信任 connect 时缓存的 `wm size`**(横竖屏切换/`wm size` 被改都免疫,任意机型不写死);② `android_screenshot` 结果文本注明分辨率并写明「坐标 = 截图原始文件像素;read_image 注明 multiply coordinates by k 时先把图上坐标乘 k」;③ tools 插件里 tap/double_tap/swipe/scroll 描述同步写明换算规则。

## 37. 坏插件导致 dsh web / runtime 启动超时无法恢复:坏插件自救自动禁用(v0.113.1)

**现象**:装入并启用某个 `dsh` 插件(如 `dsh-status-rotator`)后,重启 StarHub 时卡在 dsh web / runtime 启动,约 60s 后报「就绪探测超时/initialize 失败」;而且插件一直处于 `enabled`,每次重启都死在同一处,连设置页都进不去(网页从未起来)。

**根因**:dsh 组合的 boot() 会跑 `assertEntriesActivated`,任何一条 entry 激活失败(常见于用户插件的 **node 半 `apply()` 抛错**)都会让整个组合 `fail-loud`——`installFailLoud` 写 stderr 后 `process.exit(1)`。StarHub 侧:
- `web.rs::spawn` 只轮询 `GET /` 等 200,进程退出后永不 200,耗满 `READY_TIMEOUT`(60s)才 `kill` 并报 `ReadyTimeout`;
- `HarnessManager::initialize` 的 `runtime.call("initialize")` 在进程退出后 RPC 超时/断开。

插件仍留在 `registry.json`(enabled=true),下次重启 `sync_user_client_plugins` / `prepare_runtime_config` 又把它加回组合 → 死循环。B-4 已把「坏插件自救」列为 TODO,但首版只做了手动引导(去设置页禁用),而 web 起不来时设置页不可达。

**修复**(坏插件自救,B-4 TODO 落地):
- `plugins.rs` 新增 `disable_user_plugins`:禁用全部**非内置且已启用**的用户插件(保留目录与 registry),写回 registry.json + 重写 entries yml,返回被禁用列表,幂等。
- `web.rs::spawn` 就绪探测**提前感知子进程退出**(`child.try_wait()`),不再空等满 60s;超时/退出时自动禁用用户插件并 `spawn_once` 重试一次。
- `mod.rs::HarnessManager::initialize` 失败时同策略:禁用用户插件 → 弃掉损坏 runtime → 清空指纹 → 强制重 spawn。

**效果**:任何(node 半)有问题的插件不再阻塞启动;重试成功后应用回到可用状态,插件在设置页显示为已禁用、可重新启用(重新启用前可先手动排查)。坏插件目录与 registry 记录保留,不删除用户数据。

**后续硬约束**:
- 用户插件的 node 半必须能安全激活(`apply()` 不抛错);不确定时插件自身应 try/catch,或把非要 webServer/settings 的逻辑做成**轮询等待**(参照 status-rotator 的 `setInterval` + `attempts>=20` 清定时器)而非同步抛错。
- StarHub 侧新增启动失败自动禁用是「最后一道保险」,依赖 dsh 进程在 boot 阶段退出;若插件在**运行中**抛 UnhandledRejection,仍由 `installFailLoud` 兜底退出,同样会触发本自救。
- 若某插件总是导致超时而自救也失败(非插件问题,如闭包缺失),错误仍会透传,定位看 tracing 的 stderr(drain_lines 已转发)。

## 38. dsh 插件「重启 dsh web」按钮报 not allowed by ACL:新 command 漏登 commands.toml(v0.113.2)

**现象**:设置 → 插件页安装并启用某个 `dsh.client` UI 插件(如 `dsh-status-rotator`)后,点「重启 dsh web」按钮报 `Command dsh_web_restart not allowed by ACL`,web 运行时不重启,新启用的插件永远进不了「插件列表」——表现为「插件装了但用不了」。

**根因**:v0.113.0 新增 `dsh_web_restart` Tauri command 时,只改了 `main.rs` 的 `generate_handler!`、`commands/harness.rs` 的定义和前端按钮,漏在 `src-tauri/permissions/commands.toml` 的 `starhub-commands` 白名单里登记。tauri 2.x 对 remote origin(127.0.0.1 dsh 主壳)的 app command 也走 ACL,未登记的 command 在运行时被 Authority 直接拒;`tauri-build` 不会因白名单缺 command 报错,`cargo check`/前端 `tsc` 全绿,只有远端真点按钮才暴露——与 §33 同源的老坑又踩了一遍。

**修复**(v0.113.2):在 `permissions/commands.toml` 的 `commands.allow` 列表里 `dsh_shutdown` 与 `dsh_web_url` 之间补 `dsh_web_restart`。

**复盘**:§33 的教训「增删/重命名任何 Tauri command,`generate_handler!`、`permissions/commands.toml`、前端调用方三处必须同一 commit 同步」这次仍没被严格执行。ACL 清单的同步是纯手工的,无任何 gate 拦截——建议后续用脚本从 `main.rs` 的 `generate_handler!` 收集注册命令并 diff 清单,缺即报错,把这道手工程序化。
